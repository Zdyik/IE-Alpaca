# 特征工程说明

## 1. 核心决定：一切风险特征都走「速率」

原始事件计数与里程天然正相关 —— 一辆跑了 10000 km 的车，什么事件都比别人多。
**直接把计数喂给模型，模型学到的是「里程」而不是「风险」**，最后交出「跑得多
风险高」的结论：AUC 平庸，任务二的可解释性更是没法看。

因此所有风险特征的主轴一律是速率：

```
每千公里事件率 = 计数 / 里程 × 1000
每百小时事件率 = 计数 / 行驶小时 × 100
```

速率还有一个**决定性**好处：**对窗口长度不敏感**。

这一点直接决定了整个标签方案能否成立。赛题给的数据只有 60 天，而前瞻期是 40 天，
于是只能用「前 20 天特征 → 后 40 天标签」来自造监督信号。此时训练窗口是 20 天，
而最终的推理窗口是全部 60 天 —— **窗口长度不一致**。用绝对计数会直接崩，用量率
则基本消除差异。这是「速率为纲」的第一理由，而不是风格偏好。

分母从轨迹实算（`distance` 单位是**厘米**，需除以 1e5 转 km；轨迹本身给出
`run_time` 秒），车辆画像的近半年月均值作为交叉校验（`km_vs_profile_ratio`
可用来发现暴露量数据本身有问题）。

## 2. 两级架构：为什么先做日粒度聚合

最重的两类数据是轨迹（数十 GB、轨迹点级）与 IMU（更高频）。而特征需要按**任意
时间窗口**计算（多起点增广要求 `[1..t]` 这种可变长度）。若每次都重扫原始数据，
代价无法接受。

因此：

1. `features/daily.py` 只扫一遍原始数据，压缩成 `(gpsno, date)` 粒度的小表；
2. `features/build.py` 在这些小表上做窗口切片与聚合，任意窗口都很便宜。

副产品是**口径天然一致**：保险箱（`t=20`）与增广样本（`t=5/10/15`）共用同一份
日粒度表，不会出现两套算法算出两种数的情况。

日粒度表的 schema 就是模块之间的契约，写在 `features/build.py` 顶部。

## 3. 六组特征

| 组 | 代表特征 | 设计意图 |
|---|---|---|
| **G1 暴露量** | `km`、`hours`、`active_days`、`night_km_share`、`highway_km_share`、`profile_*` | 提供所有速率的分母；画像提供长期行为基准 |
| **G2 事件族速率** | `count_{族}`、`rate_per_1kkm_{族}`、`rate_per_100h_{族}`、`share_{族}`、`rate_severity_per_1kkm` | 主信号。计数保留一份是为了让模型能区分「率低但绝对量高」 |
| **G3 时间结构** | `night_event_share`、`dawn_event_share`、`weekend_event_share` | 同类事件发生在深夜与发生在白天，风险含义不同 |
| **G4 趋势与集中度** | `log_rate_ratio_late_early`、`weekly_rate_slope`、`max_day_share`、`day_gini` | 区分「偶发一次」与「长期慢性风险」。Gini 高的车是爆发型，低的是持续型 |
| **G5 高危 recency** | `count_code_11803/11804`、`days_since_last_ultra`、`has_ultra_in_window` | 行为复发效应，几乎必然是最强的单特征 |
| **G6 覆盖度与删失** | `compliance_count/share`、`trajectory_coverage_ratio`、`event_days`、`low_coverage_flag`、`has_imu` | **防「沉默即安全」**，见下节 |

事件族定义与逐事件码的严重度权重都在 `configs/base.yml`。族之间**不做互斥假设**
（出题方参考文档明确提示风险触发不互斥），因此同一事件可以同时计入多个族的特征。

## 4. 「沉默即安全」这个陷阱

这是这类数据里最隐蔽的错误来源：

> 摄像头被遮挡、设备离线、车辆长期停驶 —— 这些情况都会让某台车的事件数**变少**。
> 如果模型只看事件数，就会把「看不见」判成「安全」，于是**真实高风险的车拿到高分**。

两道防线：

1. **显式覆盖度特征**：`compliance_share`（遮挡/角度异常占比）、
   `trajectory_coverage_ratio`、`event_days`、`low_coverage_flag` 直接进入模型，
   让模型有机会区分「真安全」与「没数据」。
2. **IMU 缺失不填 0**：`has_imu` 为 0 时 IMU 派生特征保持 `NaN`。LightGBM 原生
   支持缺失值，因此不需要插补；填 0 会把「这辆车没有 IMU」错误地编码成
   「这辆车 IMU 事件为 0」。

这条也写进了任务二的运营边界：设备遮挡可能让真实高风险的司机拿到高分，因此
合规维度单独计权，并建议对低覆盖度车辆做人工复核。

## 5. IMU：提升阶梯而非保底路径

出题方的《IMU 数据风险分析参考资料》其实是一张**坑位地图**。逐条对到实现上：

| 文档提示 | 实现里的对应动作 |
|---|---|
| IMU 有噪声/异常/不可用时段 | 特征带 `imu_coverage_days`、`imu_coverage_ratio` |
| **设备姿态未必水平** | 用整段加速度均值估计重力方向定垂直轴，取水平面内方差最大的方向为车辆前向轴，把三轴投影到车辆坐标系。**不做这步 `accel_x` 根本不是前后方向**，急刹车特征全错 |
| 不同车型阈值不同 | 用**每车自适应**阈值 `median + k×MAD`（MAD 对异常值稳健，不会被事件本身拉偏） |
| 风险不互斥 | 急转弯与猛打方向共用横向信号但分别计数，不做互斥 |
| EMS 与 GPS 速度各有优劣 | 字段都保留，特征层只用事件计数，速度交叉验证留给后续 |

**但实现刻意把它放在提升阶梯**：IMU 是压缩包、只覆盖部分车辆、需要姿态校准与
自适应阈值，一周内做对的风险很高。因此 `build_daily_imu` 在缺少数据时返回 `None`
而不是抛错，让保底路径（事件 + 轨迹 + 画像）能独立跑通。

姿态标定与阈值估计用**每车抽样**（默认前 20000 行）而不是全量两遍扫描，这是
成本与精度的取舍，在此显式写明。

## 6. 免费锚点：无需标签就能验证特征抽对了没有

这是被大多数人浪费掉的反馈通道。出题方给了六类 IMU 场景的**定量频次量级**
（每 100 辆车每月）：

| 场景 | 文档量级 |
|---|---|
| 急加速 / 急刹车 | 数千次 |
| 急转弯 / 猛打方向 | 数百次 |
| 疑似碰撞 | < 100 次 |
| 疑似侧翻 | < 10 次 |

抽出来若差一两个数量级，就是阈值算错了，与模型好坏无关。`audit/anchors.py`
把它写成可执行检查（`check_imu_magnitude`）。

事件数据上有等价的检查，而且**第 1 天就能做**：

- **频次序关系**：`疲劳/分心/超速 ≫ 跟车/盲区 ≫ 未遂事故 ≫ 事故`。
  违反序关系说明数据或标签定义有问题，此时应停下来查数据，而不是继续调模型。
- **符号约定**（训练后）：各风险族与标签的相关应为正。若某族显著为负，先怀疑
  混杂（典型是遮挡造成的删失），**不要庆祝模型发现了新规律**。

## 7. 特征字典

`reports/feature_dictionary.csv` 记录每个特征的**组 / 名称 / 定义 / 时间来源**。
时间来源一栏不是装饰：它是泄漏审计的兜底证据 —— 允许的取值只有
「特征窗口」与「画像（半年，早于窗口）」，`models/leakage.py` 会核对它是否被违反。

更强的检查是**截断不变性**（见任务一说明第 4 节）：用截至特征窗口结束的数据重建
特征，与用全量数据重建的特征必须逐格一致。这检查的是**行为**而不是**声明**，
因此比人工核对可靠得多。
