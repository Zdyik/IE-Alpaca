# IE-Alpaca · 驾驶安全赛题参考实现

2026 Agent 大赛《驾驶安全》赛题（G7 易流）的完整可复现实现，覆盖两个任务：

| 任务 | 内容 | 评分方式 | 提交物 |
|---|---|---|---|
| 任务一 | 用 500 台车过去 60 天的驾驶行为，预测每台车**未来 40 天是否发生事故（含未遂事故）** | **AUC** 排序 | `outputs/task1_prediction.csv` |
| 任务二 | 可解释、可运营、可判别的司机安全评价模型 | 人工评审（区分能力 35% / 可解释性 25% / 可运营性 20% / 完整性 20%） | `outputs/task2_scores.csv`、安全卡 |

> **本仓库不含任何赛题数据、赛题 PDF、提取码或车辆级结果。**
> 赛题规定「不得泄露任何数据中涉及的信息」，而本仓库是公开的，因此
> `scripts/98_compliance_check.py` 会在每次运行时扫描并阻止此类内容入库。
> 结果 CSV 只通过赛方官方渠道提交。

---

## 1. 核心设计（三句话）

1. **标签从哪来**：赛方只给了 60 天数据，而前瞻期是 40 天 —— 我们没有标注样本。
   但事件数据里有 `11803 事故` 与 `11804 未遂事故`，于是用**时间切分自监督**：
   前 20 天作特征窗口、其后 40 天作结果窗口。`60 = 20 + 40` 不是巧合，是唯一能让
   40 天结果窗口落在观测期内的整数切分。
2. **特征怎么算**：全部转成**速率**（每千公里 / 每百小时）。原始计数与里程天然
   正相关，直接用计数会让模型退化成「里程预测器」。速率还有一个决定性好处 ——
   **对窗口长度不敏感**，这正是上面那个切分能成立的前提。
3. **怎么知道对不对**：搭一条四层反馈链，其中专门有一层用来**证伪自己**。
   详见 [`docs/03_任务一算法说明.md`](docs/03_任务一算法说明.md) 第 4 节。

## 2. 快速开始

### 2.1 安装

```bash
python -m venv .venv
# Windows
.venv\Scripts\python.exe -m pip install -r requirements.txt
# Linux / macOS
.venv/bin/python -m pip install -r requirements.txt
```

### 2.2 没有真实数据也能跑（推荐先做这一步）

仓库自带**合成数据生成器**，可以在拿到赛题数据之前验证整条链路：

```bash
python scripts/01b_make_synthetic.py --out data/raw/synthetic --vehicles 120
python scripts/99_verify.py --quick        # 端到端自检，应输出「全部通过」
```

> ⚠️ 合成数据有**已知的生成过程**，用途是验证「打乱标签后 AUC 必须回到 0.5」
> 这类断言确实成立。**其上的任何指标都不代表比赛结果。**

### 2.3 用真实数据跑

1. 把四个数据集（车辆画像 / 风险事件 / IMU / 轨迹）放入 `data/raw/`。
   脚本按**列签名**自动识别，不依赖文件名，因此文件名可以任意。
2. 依次运行：

```bash
python scripts/02_audit.py       # 数据审计 + 标签口径闸门 + 免费锚点
python scripts/03_features.py    # 六组特征 + 特征字典
python scripts/04_task1.py       # 任务一：基线 / CV / 九项闸门 / 四类负对照 / 保险箱
python scripts/05_task2.py       # 任务二：可加性评分 / 安全卡 / 运营建议
python scripts/06_docs.py        # 导出 PDF
python scripts/98_compliance_check.py   # 入库合规校验
```

Windows 下一键：

```powershell
pwsh -File run_all.ps1
```

`02_audit.py` 会输出 `reports/label_decision.json` —— **它是整个项目的决策闸门**。
若事故样本过于稀疏，它会自动给出降级方案（并入前碰撞预警作代理标签、或缩短结果
窗口提高基率），并把理由写进报告。**降级必须被显式记录，不允许静默发生。**

## 4. 验证协议（这个项目最该被看的部分）

在 N=500、正例率约 20% 的条件下，AUC 的抽样标准误约 **0.031** —— 也就是说
`AUC = 0.72` 的 95% 置信区间是 `[0.66, 0.78]`，**CV 上 0.72 与 0.76 的差距在统计上
不可区分**。因此本项目的验收不是「涨了多少」，而是三道关卡：

**① 相对层**：必须显著超过最强单特征基线（B1 = 特征窗口内事故+未遂事故计数）。
判据是配对 bootstrap 的 ΔAUC 95% CI 不含 0。

**② 绝对层**：`<0.60` 不合格 / `0.65–0.72` 合格 / `0.72–0.80` 良好 /
`>0.85` **默认判定为泄漏**，先过审计再谈。

**③ 稳健层**：训练−验证差 ≤0.10、打乱标签回到 0.45–0.55、跨期 ΔAUC ≤0.10、
交叉验证必须 `GroupKFold by gpsno`。

### 四类负对照

都在**完整流水线上**跑（含特征准备与模型选择），而不是「打乱标签跑一次固定模型」
—— 后者测不出选择偏差，而那正是最可能骗到自己的力量：

| 对照 | 期望 |
|---|---|
| 标签置换 | AUC ∈ [0.45, 0.55] |
| 影子标签（同基率随机 0/1） | AUC ∈ [0.45, 0.55] |
| 时间倒置（特征取结果窗口、标签取特征窗口） | AUC ≤ 0.60 |
| 随机特征注入（等量噪声列） | ΔAUC ≤ 0.02 |

### 保险箱

跑 200 组实验挑最好的，CV AUC 期望虚高约 **+0.08** —— 什么都不做也能「得到」0.80。
因此 `t=20` 的主样本全程锁死，只在最终评估时开一次，每次开启都记进
`reports/vault_audit.jsonl`。

## 5. 已知局限

这些必须写清楚，而不是藏起来：

1. **代理标签与真实任务之间存在无法闭合的差距。** 我们永远拿不到未来 40 天的真实
   标签，一切数字都建立在自监督构造上。报告里给出的置信区间只覆盖「代理任务内部」
   的抽样误差，**不覆盖代理与真任务之间的差距**。
2. **训练窗口（5/10/15/20 天）与推理窗口（60 天）长度不一致。** 缓解措施是所有
   风险特征主轴都是速率（对窗口长度不敏感），但这是缓解而不是消除。
3. **事件与轨迹的经纬度坐标系是否一致尚未确认**，因此位置/路况校正被放在提升
   阶梯而非保底路径 —— 坐标系若不一致，热点会错位。
4. **IMU 只覆盖部分车辆**，特征层对缺失保持 `NaN` 而不填 0（避免把「没数据」当成
   「没风险」），并单独给出 `has_imu` 标志。
5. **任务二的绝对分是车队内分位数**，因此跨车队、跨时期的绝对分不可直接比较，
   应看排名与趋势。
